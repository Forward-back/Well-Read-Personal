# 精读 Agent 采用四段流水线与双模型分层

## 背景

现有精读已经是逐窗口的结构化循环：每轮读取一个窗口，模型输出理解、问题、结论、术语与矛盾，代码机械校验 quote 是否逐字存在于 chunk，失败时触发检索补证，并用步数与 token 预算限制运行。问题不在“有没有结构化”，而在四件事：

1. 缺少全文结构预读，逐节推进容易失去论证地图。
2. 每轮最多抛 4 个问题，交互密度高，用户容易从“读者”退化为“答题者”。
3. 只有结论、术语、未决与矛盾的局部摘要，没有完整的用户理解档案与阅读任务记忆。
4. 精读完成后没有自测遍，读、问、复习仍是三段断开的学习链路。

同时，精读模型被强制要求支持 thinking，逐窗口抽取也使用同一强模型，成本与延迟都偏高。

## 决策

1. 精读采用四段流水线：结构预读、逐章循环、全局综合、自测出卡。四段共享同一运行状态机与持久化，不引入任何 agent 框架。
2. 保留 `grill-with-docs` 作为产品口径，但不把它当作完整运行时 skill。只保留追问模糊表述、追问逻辑跳跃、引用原文的原则；交互节奏、上下文假设与工具边界由精读引擎自己控制，仍不与普通问答共享可执行工具。
3. 逐章循环先给理解陈述，再由用户确认；每章最多一个提问。快速档不提问，标准档与逐条档每章最多一问；连续跳过两次后进入安静模式，只产笔记，不再等待确认。深度只改变窗口大小与章节数量，不提高单章提问上限。理解陈述确认是低门槛确认，不计入提问预算。
4. 每轮结束后蒸馏三类记忆：知识图谱（术语、已确认结论、矛盾、章节要点）、用户理解档案（确认率、错答点、跳过概念）、任务记忆（目标、进度、预算）。只把蒸馏态带入下一轮，不常驻整篇文档与完整对话。
5. 引用继续使用机械校验：quote 必须逐字包含于对应 chunk；失败由代码触发检索补证；没有证据的内容不得写成结论。JSON 输出增加严格 schema 校验，失败重试一次，再失败标记本轮降级。
6. 模型分两层：抽取模型负责结构遍与逐章抽取，可配置为非 thinking 的便宜快模型；综合模型负责全局综合、问题判定、矛盾裁决与自测判定，必须支持 thinking。两个角色都未配置时回退现有精读模型；只有抽取角色配置时，综合角色回退现有精读模型。
7. 自测遍按章节产出带引用与答案的自测题；运行结束后生成预览，用户选择卡组与题目后手动导入复习 V3。不静默创建复习卡，不绕过复习查重与吸收规则。
8. P0 只交付引擎闭环。原文批注、费曼自述、概念实体层、论证图、目标驱动与新颖度过滤、遗忘驱动重读、读者画像、MCP 读取工具均不进入 P0。
9. MCP 工具面保持固定 17 个；精读成果通过页面与后端接口提供，不新增 MCP 工具。若未来扩展，先单独修订 MCP 硬规则并写 ADR。

## 考虑过的替代方案

- **继续使用单模型全程 thinking**：改动小，但结构遍与逐章抽取的成本和延迟不变，且与精读深度档位脱节。
- **引入 Python agent 框架**：可复用现成编排，但与 Go 单体、本地部署和现有结构化循环冲突，调试与依赖成本更高。
- **完全移除 `grill-with-docs` 口径**：概念更干净，但会让现有产品规则、前端文案与文档同时改口径，收益不足以抵消迁移成本。
- **自测题自动创建复习卡**：链路更短，但会绕过用户选择与查重吸收，容易制造重复卡和错误归属。
- **新增 MCP 精读读取工具**：外部可访问性更好，但与当前固定 17 工具与只读边界冲突，需单独决策。

## 后果

- [精读agent需求](../02-需求与设计/03-精读/精读agent/精读agent需求.md) 与 [精读agent开发方案](../02-需求与设计/03-精读/精读agent/精读agent开发方案.md) 成为精读引擎优化的执行依据。
- 精读设置从单一模型扩展为抽取模型与综合模型两个角色；现“精读模型必须支持 thinking”的规则按角色调整。
- 新运行使用 `state_version=3`；已有 `state_version=2` 的结构化运行继续按旧引擎完成，不强制迁移。
- 逐章提问上限从每轮 4 个降为每章最多 1 个；深度档位通过窗口大小与章节密度体现，而不是提高单章提问数量。
- 精读与复习形成“阅读 → 自测 → 预览 → 导入复习卡”闭环，但不自动写卡。
- MCP 工具面不变，精读成果暂不对外部 AI 客户端开放。
