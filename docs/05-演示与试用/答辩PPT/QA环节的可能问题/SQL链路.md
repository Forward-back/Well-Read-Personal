# SQL 链路 · 答辩问答

> 用途：答辩 Q&A 速查。
> 核心口径：**模板解决高频确定性问题，语义索引解决“找表/找字段”，LLM SQL 兜底开放问法，执行护栏保证只读安全。**
> 优先准备：Q1（为什么不用纯 LLM）、Q2（模板与 LLM 分工）、Q8（SQL 安全）、Q9（行数/连接）、Q11（ACL/KB）、Q18（出错了怎么办）。

> 口径提醒：PPT 写“结果截断 500 行 / 连接 ping 自愈”。当前代码实际是**结果侧截断 100 行**，连接是单连接+线程锁，**没有自动 ping 重建**。被追问时按“有上限、当前 100；连接异常返回空，自动重建是待补”回答，不要硬说已实现 500/ping；建议后续统一代码或改 PPT 口径。

## 一、为什么不用纯 LLM SQL

### Q1：为什么不用纯 LLM 生成 SQL？

三个原因：

1. **不稳定**：同一个问题每次可能换一种写法，结果不可复现，评测和审计都难；
2. **慢且贵**：每次都要 LLM 调用，高频模板问题没必要；
3. **能确定性解决的部分尽量确定性**：高频查询模式用模板，规则可测试、结果可复现。

LLM 不是不用，而是放在**模板覆盖不到**的开放问法上；确定性优先，LLM 兜底。

### Q2：L1 模板和 L3 LLM SQL 怎么分工？什么时候走哪个？

按顺序：

1. 规则预筛：问题命中表触发词/计算意图才进入 SQL 链路；
2. L1 模板链：极值 → 计数 → 代码反查 → 列举/定点查询 → 字段字典；
3. L2 模糊字段：列语义索引词重叠直接答（不生成 SQL）；
4. L3 LLM SQL：模板没命中、或模板执行空结果时兜底；
5. L4 执行护栏：所有 SQL 统一校验后执行。

模板覆盖“高频、模式固定”的问题；LLM 覆盖“模板没写过、但能映射到已知 schema”的问题。两者不是二选一，是分层。

### Q3：模板按查询模式写，不按表写，具体怎么落地？新表要改代码吗？

模板的触发是“问题模式 + 表触发键”，不是给每张表写一条 SQL：

- 表触发词决定候选表；
- 查询模式决定 SELECT 列、WHERE、聚合、LIMIT；
- 表名/列名从 `schema_registry` 和 `tables_structured` 反查，不硬编码真实表名。

新表入库时注册 `schema_registry` 和表描述，L2 语义选表、L3 schema 剪枝可以自动接上；但新的**查询模式**仍可能需要加模板或靠 LLM。不是“接表即零代码全自动”。

### Q4：`schema_registry` 是什么？字段、样例值、注释从哪来？

它是结构化表格的字段目录：表名、列名、类型、样例值、别名、所属 KB。

- 字段名/类型/SAMPLE 来自表格解析注册；
- 中文 COMMENTS 从字段字典表（清分交易）并入；
- 别名把“站所/运营方/路段”等口语词映射到规范列；
- 启动时构建列语义索引，按 KB 分片。

它解决的问题是：LLM 和模板都需要知道“有哪些列、列是什么意思”，而不是让模型猜代码表名。

### Q5：L2 语义索引怎么工作？jieba 词索引和表 embedding 是不是重复？

两层，职责不同：

- **列语义索引**：表名+列名+别名+样例值+COMMENTS 分词，词重叠打分，解决“与金额相关的字段有哪些”这类模糊字段问法；
- **表描述 embedding**：表名+列名+样例值拼成描述做向量，解决关键词剪枝没命中时的语义选表（余弦 top-2，阈值 0.3）。

一个是词级字段匹配，一个是表级语义匹配；不是重复，是粗细两层。

### Q6：schema 剪枝怎么做？没命中怎么办？

先用表触发词命中表；命中后只把这几张表的 schema 送进 LLM，避免全库 schema 撑爆 prompt。

触发词没命中时，用表描述 embedding 做语义选表，取 top-2；仍无命中就跳过 SQL，不硬生成。

剪枝的收益是 prompt 更短、选表更准；代价是触发词/表描述没覆盖的新表可能漏掉，需要补注册或走语义兜底。

## 二、SQL 生成与安全

### Q7：LLM SQL 怎么防幻觉？模型自造列名怎么办？

三层约束：

1. prompt 只给剪枝后的真实 schema，要求列名只能从给定列表选；
2. few-shot 覆盖分组、计数、极值、多条件等常见模式；
3. 生成后统一走 `_validate_sql` 和执行；列名不存在会执行失败，返回空并回退/跳过，不会伪造结果。

没有“生成后再做列名语义校验”的额外一层；执行失败是最后一道现实校验。列名自造会被数据库拒绝，不是靠模型自觉。

### Q8：SQL 安全怎么保证？会不会被注入或执行写操作？

当前护栏：

- `sqlparse` 只允许单条 `SELECT`，多语句/非查询直接拒绝；
- 表白名单只允许 `tables_structured`、`schema_registry`；
- 危险模式黑名单：`INTO OUTFILE`、`LOAD_FILE`、`SLEEP`、`INFORMATION_SCHEMA`、`GRANT` 等；
- 先剥注释再匹配，防注释绕过；
- KB 白名单用严格字符集校验后拼 `AND knowledge_base_id IN (...)`，非法 ID 直接拒执行；
- LLM SQL 如果缺少 `table_name` 条件，注入 KB 作用域失败就拒执行。

边界：SQL 本身没有统一强制注入 `LIMIT`，行数上限在结果侧做；LLM 仍可能生成低效 SQL，靠表规模和超时/失败返回兜底。不是“形式化验证级”的安全。

### Q9：结果行数、超时、并发怎么控？连接断了怎么办？

- 结果侧当前截断 **100 行**（PPT 写 500，代码实际 100，需统一口径）；
- SQL 文本没有统一强制 `LIMIT`，模板里高频查询自带 LIMIT，LLM SQL 依赖 prompt 示例；
- 单连接 + 线程锁，SQL 查询串行，避免 Flask 多线程共享连接出错；
- 执行异常返回 `None`，不影响文档检索主链路；
- **没有自动 ping 重建**：服务端闲置断连时，当前查询会失败返回空，下一次能否恢复取决于连接状态；自动重连是待补项。

被追问时不要硬说 500/ping 已实现；可以答“当前是 100 行上限和失败返回空，自动重建在待办里”。

### Q10：空结果回退怎么做的？会不会死循环？

模板执行空结果时，回退 LLM 路径**重试一次**；LLM 结果再空就结束，返回无 SQL 候选。

只回退一次，不递归、不循环；模板错、LLM 也错时，最终由文档检索回答，不伪造结构化结果。

### Q11：KB、ACL、密级怎么进 SQL？会不会越权？

- `kb_ids` 通过 thread-local 传入，模板/LLM SQL 统一拼 `knowledge_base_id IN (...)` 行级作用域；
- KB 白名单非法（含引号等）直接拒执行，宁缺毋滥；
- SQL 结果密级按所涉 `tables_structured` 行所属文档的最严格值计算；
- 外层还有 ACL/密级/部门过滤，SQL 候选不能绕过。

SQL 不是“先查全库再过滤”，而是行级作用域和候选级过滤双重约束。

## 三、结果与边界

### Q12：SQL 结果怎么进入最终答案？会变成引用吗？

SQL 结果是独立候选，`answer_hint` 以 `[结构化查询结果]` 进入上下文；数据查询类问题会收紧文档上下文上限（约 4 条），因为答案主体在结构化结果里。

SQL 不是 chunk，没有普通文档引用；回答可以带表格/数值，但不会伪装成某一段原文引用。需要出处时，仍以文档引用为准。

### Q13：多表 JOIN、复杂聚合支持吗？

支持有限的单表 JSON 行查询和多条件过滤；JOIN 只在白名单表内允许。

复杂多表 JOIN、窗口函数、跨表口径需要 LLM 生成，但没有专门的 schema 关系图/外键约束，准确率不保证；当前重点是单表结构化问数，不是通用 BI。

### Q14：日期、同比、环比、中文口语怎么处理？

- 日期/数值类型靠 `schema_registry` 的类型与样例值，prompt 要求 CAST；
- 同比/环比、排名、极值由模板覆盖一部分，其余交 LLM；
- 中文口语/别名靠 `TABLE_ALIASES`、`COLUMN_ALIASES` 和表描述；
- 模板只覆盖已知模式，没覆盖的表达走 LLM，仍失败则退回文档检索。

不要承诺“任意口语都能转 SQL”；当前是高频模式 + LLM 兜底。

### Q15：模板覆盖哪些高频问题？为什么是这些？

覆盖的是数据里真实高频、且模式稳定的问法：清分交易统计、存款准备金率、信用卡指标、基础信息统计（站所/运营公司/路段/经纬度/代投点）等。

选择标准是“问题模式可枚举、结果要可复现、LLM 容易写错”；低频开放问法留给 LLM。模板不是越多越好，维护成本和误触发也是成本。

### Q16：新表、字段变更怎么适配？

- 新表入库注册 `schema_registry` + 表描述，L2/L3 可以发现；
- 字段变更后重建 schema 索引/表描述索引；
- 新查询模式需要加模板或依赖 LLM；
- 别名/触发词需要维护，否则关键词剪枝会漏。

“自动适配”只到 schema 发现层，业务口径和模板仍要人维护。

### Q17：SQL 链路的准确率怎么评？有执行准确率/数据集吗？

没有单独的 SQL 执行准确率基准；现有评测是端到端问答准确率 + badcase 抽检。

严格评法应固定问题集，分别看：SQL 可执行率、结果正确率、选表/选列准确率、空结果率、越权拦截率。当前没有这套 SQL 专项评测，答辩时不要报一个“SQL 准确率 9x%”。

### Q18：模板或 LLM 生成错了，用户会看到什么？

- 模板空结果 → LLM 重试一次；
- LLM 也失败/不安全 → 返回无 SQL 候选，走文档检索；
- SQL 执行异常 → 记录日志、返回空，不影响主链路；
- 不会把错误 SQL 的异常结果硬塞给用户，也不会执行写操作。

用户可能看到“文档回答”而不是“精确表格答案”，这是降级，不是伪造。

### Q19：为什么 SQL 只读？如果业务要更新数据怎么办？

SQL 链路的定位是**问数**，不是业务写入。只读护栏（SELECT-only、白名单、危险函数）保证 LLM 不能改库。

业务写入走 app 的业务接口和权限体系，不通过 Text-to-SQL；两者边界不能混。

### Q20：这套 SQL 链路什么时候不适用？

- 问题没有结构化表可映射：纯政策解释、跨文档比较；
- 表结构/字段含义没注册：schema 不存在，LLM 也猜不出来；
- 需要复杂多表 JOIN/窗口函数：当前没有关系图，准确率不保证；
- 数据量很大且没有索引/LIMIT：单连接串行 + 结果截断，可能慢；
- 需要强一致事务/写操作：SQL 链路只读，不适用。

一句话：SQL 链路解决“表里有的数”，不解决“文档里的道理”，也不替代业务写入。
