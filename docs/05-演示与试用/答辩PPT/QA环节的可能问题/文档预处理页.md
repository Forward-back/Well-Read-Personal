# 文档预处理页 · 答辩问答

> 用途：答辩 Q&A 速查。
> 口径：先结论，再机制，最后边界；未测指标不硬报，开源组件不自称自研。
> 优先准备：Q1 表格、Q7 页分类、Q8 OCR、Q14 清洗、Q15 双 chunk、Q18 评测口径。

## 一、已有问题优化

### Q1：为什么统一转成 Markdown？表格转成 Markdown 结构不会散吗？

统一 Markdown 是为了给下游一个稳定的文本契约，**但不是所有格式都只剩一份 Markdown**。

- 普通文档（PDF/Word/PPT/HTML 等）转 Markdown，检索、分块、引用只面对一种结构；
- xlsx **另走结构化通路**：原始表格文件推给检索侧做结构化解析/Text2SQL，行列和字段语义不靠 Markdown 表格硬扛；
- 只有解析失败或超限时才回退 Markdown 表格。

所以表格不会因为“统一转 Markdown”而必然丢关系。真正的边界是合并单元格、跨页表、复杂表头，这部分仍需人工确认或结构化模板。

### Q2：图片描述用什么生成？模型幻觉了怎么办？

图片由多模态模型生成两类结果：**OCR 文本** 和 **内容描述**，分别落成 `image_ocr` / `image_caption` 子块，并保留原图引用。

面对幻觉，实际做法是：

- OCR/描述失败或返回空内容时**不入库**，只记录失败；
- 描述只作为辅助语义，**关键事实以 OCR 原文和原图为准**；
- 检索命中后可以回到原图核对；
- 复杂图表建议人工抽检，不把描述当成唯一事实源。

幻觉风险仍然存在，不能承诺零幻觉；我们能承诺的是“描述不冒充原文、失败不伪造内容、出处可回看”。

### Q3：有开源的解析器，你这一层的价值在哪？

我们**不是从零写解析器**，而是把 MarkItDown、OpenDataLoader、pypdfium2 等引擎接进来，按格式和页类型路由。

这一层的价值在解析之后的工程链路，而不是单点解析算法：

- 逐页判断文本页/扫描页，混合 PDF 也能处理；
- 页眉页脚、水印、隐藏文字、乱码字符的清洗；
- 图片/扫描页的 OCR 与描述补全；
- 元数据、稳定 chunk、ACL、版本、引用锚点的衔接；
- 解析引擎可替换，下游契约不变。

单看 PDF 解析算法，成熟开源引擎更强；单看“从文件到可治理知识块”的整条链路，这一层才是我们的差异。

### Q4：PDF 文本噪声、非法字节具体指什么？

分两类：

- **文本层噪声**：每页重复的页眉/页脚/页码、侧边水印和窄条、目录与正文重复段、图表坐标轴碎屑；扫描页如果带低质量嵌入文本层，也不能直接信。
- **编码层噪声**：私有字体产生的不可打印字符、损坏的 UTF-8、代理字符、占位字形、软连字符断词。

对应处理：跨页重复行按“出现在多数页”阈值剔除；隐藏/离页文字过滤；页边水印和图表碎屑过滤；占位符和断词修复；非法 UTF-8 在 docreader 和 Go 侧统一清洗。边界是规则型清洗，复杂版式仍可能误删或漏删。

### Q5：清洗对最终 87.9% 的贡献多少？单独评测过吗？

**没有做过清洗的单独消融，不能把 87.9% 直接归因于清洗。**

87.9% 是端到端问答准确率，解析/清洗只是其中一环。清洗的主要价值是消除硬失败：乱码、重复页眉、隐藏文本、非法字节导致的坏向量，而不是直接提升语义理解。

如果要把贡献说清楚，正确的验证是：固定同一批文档和问题，对比“清洗开/关”的召回命中率、引用正确率、答案准确率。这是下一步评测计划，当前没有这个数字就不硬报。

## 二、新增高概率问题

### 格式与解析

### Q6：支持哪些格式？分别走什么解析引擎？

内置引擎覆盖 PDF、DOC/DOCX、XLS/XLSX、PPT/PPTX、Markdown、HTML、EPUB、MHTML、XMind 和常见图片。

- PPT/PPTX、CSV 默认走 MarkItDown；
- PDF 可选 OpenDataLoader；
- Office 文件会检查文件魔数，例如把旧版 `.doc` 改名成 `.docx` 会被纠正回 DOC 解析；
- 解析引擎可按知识库/上传任务选择，不是写死一条路。

### Q7：PDF 怎么判断文本页还是扫描页？混合 PDF 怎么办？

**逐页判断，不按整篇判断。**

主信号是页面图片覆盖面积（扫描页通常接近整页），辅信号是文本字符数极低但又有图片内容；扫描页渲染成图片，交给 Go 侧 OCR；文本页走原生文本层，并做阅读顺序和标题重建。

扫描页即使带一层低质量嵌入文本，也按图片走 OCR，避免信任乱码文本层。混合 PDF 按页混合处理；如果 PDF 文本层质量普遍很差，可以用“强制扫描模式”全部走 OCR。误判边界主要是图表页/文字化图片，可以用强制模式或重解析兜底。

### Q8：扫描 PDF 的 OCR 用什么？中文、表格、公式能处理吗？

用多模态模型的扫描件专用 prompt，要求保留段落层级、Markdown 表格和 LaTeX 公式，并明确忽略页眉页脚页码；空图返回“No text content”。

它不是专用 OCR 引擎，复杂表格、公式、竖排文字仍可能出错；当前也没有单独的 OCR 准确率基准，评测以端到端问答和人工抽检为主。出错时保留原图，可人工复核或重解析，不伪造文本。

### Q9：为什么解析只转图片，OCR 要放到 Go 侧？

职责分离：

- docreader 只做无状态格式转换，不持有模型凭据，也不引入 GPU/模型依赖；
- Go 侧统一做模型路由、租户配置、重试、图片落库、chunk 和 ACL 衔接；
- 换 OCR/VLM 模型不影响解析服务，解析服务也能独立扩缩容。

所以 docreader 遇到扫描页只负责渲染图片和标记来源，OCR 在 Go 侧异步完成。

### Q10：大文件、超时、并发怎么处理？

docreader 单文件 gRPC 上限 50MB，App 侧解析调用默认 30 分钟超时；失败进入解析失败状态，可重试或重解析。

PDF 因为 pdfium 非线程安全，进程内串行解析，避免并发把 PDF 库搞崩；其他格式可以并发。扫描页的 OCR/描述是异步子任务，失败不阻塞文本页入库。

### 多模态、表格与分块

### Q11：图片描述什么时候触发？成本和延迟怎么控？

只在开启多模态且文档含图片/扫描页时触发，走异步图片任务。

- 嵌入式图片先按尺寸、页面占比、跨页重复过滤，logo、水印、图标不送模型；
- 每篇文档有图片数量上限；
- OCR 和描述分开输出，失败只记录不阻塞主流程；
- 成本由知识库多模态开关和图片过滤共同控制。

### Q12：Excel 表格怎么入库？合并单元格、跨页表怎么办？

xlsx 不只是转 Markdown：

- 原始文件在限制内直接推给检索侧，走结构化表格/Text2SQL，保留行列和字段语义；
- 解析失败或超限才回退 Markdown 表格；
- 普通文档里的表格尽量按 Markdown 表格保留。

合并单元格、跨页表、复杂表头仍是边界，需要人工确认或改用结构化模板；这是我们明确承认的局限。

### Q13：图片和 OCR 结果怎么参与检索？会不会污染？

OCR 和描述分别作为 `image_ocr` / `image_caption` 子块参与检索，`ImageInfo` 保留原图 URL，引用可回到原图。

- OCR 是事实性文本，描述是辅助语义；
- 两者分开存储，避免描述幻觉直接冒充原文；
- 图片任务失败或空结果不落块，不污染索引。

### 清洗与分块

### Q14：清洗具体做什么？会不会误删正文？

清洗分四类：

- 跨页重复行：去掉重复出现的页眉、页脚、页码；
- 版式噪声：侧边水印、隐藏/离页文字、图表坐标轴碎屑；
- 字符层：占位字形、软连字符、损坏 UTF-8、代理字符；
- 结构层：统一换行、标题层级和引用标记。

只做规范化，不改写正文。重复行用“多数页出现”的阈值，合法重复内容（例如每页都出现的表头）有被误删的可能，这是已知边界，可通过运维参数调整或重解析。

### Q15：分块在 Go 侧还是检索侧？为什么有两套 chunk？

两套职责不同：

- **Go 侧 app chunk**：默认 512 字、80 字重叠，可配置 parent-child（约 4096/384），承载治理、版本、引用锚点和审计；
- **检索侧 YLSW chunk**：按领域规则再切一次，负责向量召回和重排，通过 `source_chunk_id` 映射回 app chunk。

不是重复造轮子：治理粒度和召回粒度本来就不一样。Markdown 是两层共同的稳定输入契约。

### Q16：长文档、条款、表格怎么切？parent-child 是什么？

按标题、段落和表格边界切；超长章节切窗口，表格尽量整块保留，避免把一行/一列切散。

parent-child 是父块保留上下文、子块用于向量召回：召回命中子块，再把父块给模型，兼顾精度和上下文。代价是存储和索引更多，需要按知识库配置启用。

### 元数据、质量与运维

### Q17：文号、机构、日期、密级、部门这些元数据怎么来？LLM 抽错了怎么办？

两条路：

- 文件名里的 UMS 规则先做确定性抽取：文号、机构、日期、产品等；
- LLM 再补生命周期、密级、部门、替代关系等语义字段，低置信度进入待确认，不直接采用；
- 人工表单可以覆盖。

元数据只用于过滤和排序，不进入答案正文；抽错可以修正，生命周期等高风险变更还会写审计。

### Q18：解析质量怎么评测？87.9% 是什么口径？

87.9% 是端到端问答准确率，不是解析准确率。

解析侧目前看：解析成功率、空文本率、乱码率、引用可定位率、人工抽检。没有单独的解析 F1，也没有清洗消融，所以不能把端到端数字拆给某一个组件。要严格归因，需要固定文档集做组件级对比，这是我们下一步要补的。

### Q19：扫描件没有文本、OCR 失败怎么办？

不伪造文本：

- OCR 失败或返回空内容时，图片仍在，但只保留原图引用；
- 文档会标记解析异常或内容不足；
- 用户可以重试、换解析引擎或重新解析；
- 不会把空扫描件静默入库成“解析成功”。

### Q20：如何处理隐藏文本、提示注入、SSRF 和恶意文件？

- **隐藏文本**：过滤不可见、离页、退化字形，避免隐藏指令进入模型上下文；
- **提示注入**：文档内容按不可信输入处理，OCR prompt 只允许输出文本，模型不执行文档里的指令；
- **SSRF**：URL 导入统一走 SSRF 校验和白名单，不允许访问内网任意地址；
- **文件安全**：上传类型/大小受限，解析器不执行宏和脚本，只做格式转换。

边界是解析库自身的漏洞，需要镜像更新和独立服务隔离，不能承诺绝对安全。

### Q21：重新解析或文档更新后，版本、chunk 和引用怎么办？

- 重新解析前自动生成版本快照，可回滚到重解析前内容；
- 重解析会重建分块，**旧 chunk ID 会变，旧评论锚点和进行中的 CR 会失效**；
- 历史回答的引用绑定的是版本，不随重解析漂移；
- 索引自动重推，未变化分块复用旧向量，只重嵌变化内容；
- 大改走重解析，小改走分块 CR，这是两条明确的路径。

### 边界与取舍

### Q22：为什么不让大模型直接读全文，非要做预处理？

全文直读成本高、上下文窗口有限，而且无法稳定引用到段落，也无法做 ACL、版本和审计。

预处理把文档变成可检索、可引用、可治理的块；模型只读被召回或被精读选中的范围。预处理不是为了“多一道工序”，而是为了把权限、出处和成本控制住。

### Q23：解析器可以替换吗？接入新格式成本高吗？

可以。解析引擎按知识库/上传任务选择，内置引擎、MarkItDown、OpenDataLoader 都在注册表里。

新增格式只需要实现解析器接口并注册，清洗、分块、元数据、索引的契约不变。代价是不同引擎输出质量不一致，需要评测和回退策略，不是接进来就无脑可用。
