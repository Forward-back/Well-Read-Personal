# 版本控制 · 答辩问答

> 用途：答辩 Q&A 速查。
> 核心口径：**版本快照回答“改了什么”，稳定 chunk ID 回答“引用/锚点为什么不断”，引用绑定回答“当时依据哪一版”，生命周期回答“还算不算数”。**
> 优先准备：Q1（为什么不用 Git）、Q3（版本号怎么产生）、Q6（并发修改）、Q8（回滚覆盖）、Q11（回滚与 chunk ID）、Q12（引用绑定版本）、Q13（废止 vs 版本）、Q17（快照体积）。

## 一、模型与产生

### Q1：为什么自建版本控制，不用 Git？

Git 面向代码和工程师，缺三样企业文档需要的东西：

- 角色与审批：六角色、部门/KB/ACL、CR 审批、manager 合并；
- 业务元数据：密级、部门、生命周期、引用、审计；
- 非技术用户：编辑的是分块和正文，不是仓库、分支、commit。

我们借的是 Git 的思想——**不可变快照、稳定标识、回滚生成新版本**；治理层按企业文档重做。不是把 Git 包一层 UI。

### Q2：版本是存全文快照还是 diff？为什么？体积怎么办？

存**全文快照**：每个版本把当时所有 chunk 的内容和启用状态复制到 `doc_version_chunks`。

- 好处：回滚、对比、导出都不依赖历史 diff 链，任何一版可独立还原；
- 代价：体积按“版本数 × chunk 数”增长；
- 当前没有版本压实/清理，这是已知成本；
- 方案已设计：内容寻址去重 + 保留策略 + 引用保护的 GC，但还没开发。

答辩时不要说“已经做了压缩”，说“当前全量快照，压实是下一步”。

### Q3：V1.N 的版本号怎么产生？并发会不会重号？

每次发布取当前最大 `version_seq + 1`，生成 `V1.N`；数据库对 `(knowledge_id, version_seq)` 有唯一索引。

- CR 合并会校验 chunk 当前内容和 `content_revision`，两个 CR 改同一段时后合并者会失败；
- 唯一索引是版本号竞争的最后兜底；
- 极端并发下仍可能因唯一键冲突失败，当前没有自动重试/重新取号 UX。

所以“不会静默重号”，但“并发体验”还不是最终形态。

### Q4：版本快照里到底存了什么？没存什么？

存：chunk 内容、chunk index、启用状态、chunk ID、版本来源、操作者、时间、标题/描述。

**不存**：ACL、共享关系、密级、部门、生命周期。这些是文档级治理状态，不属于内容版本。

所以“回滚内容”不会恢复旧的权限/密级；权限和生命周期是独立动作，避免用版本回滚绕过治理。

### Q5：版本快照和 chunk 修订是什么关系？

两层记录：

- `chunk_revisions`：每次改单个 chunk 前保存旧内容，支持 chunk 级恢复；
- `doc_versions` + `doc_version_chunks`：每次发布/回滚/重解析前保存全文快照，支持整篇回滚与对比。

合并和直接编辑都会写 chunk 修订；发布时再写版本快照。一个管细粒度，一个管发布点。

## 二、更新与并发

### Q6：两个人同时改同一段怎么办？

当前是**乐观锁 + 内容校验**：

- CR 里记录 `original_content` 和 `content_revision`；
- 合并时校验当前 chunk 是否仍是原文、版本号是否被改过；
- 别人先改了，后合并者返回“分块内容已被修改”，整单不合并，需刷新重提。

没有三方自动合并——这是我们明确承认的边界。方案已写入设计：行级 diff3、非重叠自动合并、冲突显式返回；当前还没开发。

### Q7：审批怎么防“自己批自己”？manager 能自审吗？

不能：

- 提交人不能审批自己的 CR，manager 也不例外；
- 合并前至少一名“其他”审阅者或部门审计员批准；
- 只有 manager 能合并；审批通过不等于合并；
- 部门审计员/reviewer 可审批/驳回，但不能合并。

当前没有强制“提交人/审批人/合并人完全三人分离”：manager 可以是审批人之一并合并，这是待补边界。

### Q8：回滚会不会把别人后来的修改覆盖掉？

会。回滚是**受控覆盖**，不是合并：

- 选定一个旧版本，按快照恢复 chunk 内容，生成一个新版本；
- 当前内容与快照不同的部分会被覆盖，但历史版本仍在，可再回滚；
- 只有 manager 能回滚，动作写审计；
- 当前回滚不要求第二人审批，这是治理风险点。

答辩时要说清楚：“回滚不是时间机器，是一次新的覆盖发布，历史可追。”

### Q9：回滚为什么只有 manager？要不要二次审批？

回滚会直接影响线上检索和引用，属于高风险动作，所以限定 manager。

当前是“二次确认 + 审计”，**没有强制第二人审批**。是否要加四眼回滚，是待决问题；在试点阶段优先保证动作可追溯、可再回滚。

### Q10：如果修改大到必须整篇重写，怎么办？

当前 CR 是分块治理，只能改已有 chunk，不能增删章节；整篇重写走**重新解析**：

- 已成功解析的文档，重解析前自动生成版本快照，可回滚到重写前；
- 重解析会重建 chunk ID，旧评论锚点和进行中的 CR 失效；
- 历史回答的引用绑定版本，不受影响；
- 全文重写 CR 是设计方向，还没开发。

## 三、回滚、引用与废止

### Q11：回滚为什么生成新版本，而不是删掉旧版本？

版本是“发布历史”，不是“当前指针”：

- 回滚 = 恢复旧内容 + 生成新版本 `V1.N+1`，历史一条不删；
- 旧版本仍可对比、可再次回滚；
- 当前版本回滚会被拒绝（“当前版本无需回滚”）；
- 回滚按稳定 chunk ID 恢复：缺失的 chunk 用快照 ID 重建，多余的置为禁用，`content_revision` 递增。

这样 issue、评论锚点、历史引用不会因为回滚失效。

### Q12：引用绑定版本是怎么做的？历史回答点进去看到哪一版？

回答落库时，每条引用写入当时最新版本的 `version_id` 和 `version_label`（如 V1.2）。

- 历史回答能说明“当时依据哪一版”；
- 点进原文看到的是**当前版本内容**，不是旧版页面；
- 引用卡会显示“依据 V1.2”，废止文档带“已废止”；
- 旧消息（功能上线前）没有版本字段，显示为空。

所以“引用绑定”锁定的是回答时的版本身份，不是把历史原文冻结在聊天里；原文片段本身随消息保存。

### Q13：废止算版本动作吗？和删除有什么区别？

不算。废止是**生命周期状态**，不是版本：

- `lifecycle_status=draft/effective/expired`；
- manager 操作，写 `knowledge.lifecycle_changed` 审计；
- 检索侧元数据原地更新，不重嵌，下次查询立即生效；
- 问答/检索默认剔除废止文档，精读显式选中仍可读；
- 不删除内容，历史版本和引用都保留。

删除是另一条链路（软删除文档、删 chunk、清索引）；废止只是“不再作为现行依据”。

### Q14：重新解析为什么先生成快照？旧锚点怎么办？

重新解析会删旧 chunk、生成新 chunk ID，不先留快照就无法回滚。

- 对已成功解析的文档，重解析前自动生成 `reparse` 来源版本；解析失败的文档没有可保留内容，不生成快照；
- 旧 chunk ID 失效，旧评论锚点/进行中的 CR 失效，这是已知代价；
- 历史回答引用绑定版本，不受影响；
- 新内容重推索引，未变化文本可复用旧向量。

所以快照保证“可回滚”，但不能保证“旧锚点不丢”。

### Q15：为什么引用绑定 version_id，而不是内容 hash？

hash 只能证明“这段内容是什么”，不能回答：

- 这是哪一次发布、谁发布、什么来源（CR/回滚/重解析）；
- 它在版本链上的位置；
- 回滚/对比/审计时对应哪一版。

version_id 带发布语义和审计信息；消息里同时保存原文片段，内容证据也不丢。两者不是二选一。

## 四、索引、保留与审计

### Q16：发布后索引什么时候一致？

合并/回滚成功后自动后台重推，最多等 5 秒追平；小文档通常立即生效，大文档继续后台同步。

- 生命周期/密级/部门等纯元数据走原地更新，即时生效、不重嵌；
- 重推失败保留 `pending/failed`，可手动重推或每日扫描；
- 因此是**最终一致**，不是强一致；发布到索引更新之间有一个短窗口。

### Q17：版本快照体积会不会失控？怎么保留？

会增长，当前没有清理：每次快照复制全文 chunk，体积按“版本数 × chunk 数”增长。

方案已设计但未开发：

- 内容寻址：相同 chunk 文本只存一份 blob；
- 保留策略：最近 N 版 + 每月一版 + 里程碑；
- 引用保护：被问答引用、合并 CR、回滚来源、合规保留的版本不自动删；
- 标记-清除 GC，先 dry-run 再分批删。

当前答辩口径：全量快照、保留全部历史，压实是下一步。

### Q18：历史版本能删吗？被引用的版本怎么办？

当前没有版本删除/保留期任务，历史全部保留；文档删除也不清理版本表，入口消失但数据还在。

未来做压实时必须先做可达性扫描：被消息引用、被 CR 指向、被回滚引用的版本不能删。不能按时间一刀切。

### Q19：版本对比是怎么做的？是行级还是 chunk 级？

按版本快照的 chunk 列表做对比，前端展示分块差异；同一位置的新旧行做成左右对照（行级 diff），不是语义 diff。

- 能看出哪段文字增删改；
- 不能自动识别“同义改写”或“条款移动”；
- 大文档对比的性能和可读性仍需打磨。

### Q20：版本快照能防篡改吗？审计能证明什么？

当前是**应用层不可变**：版本快照一旦写入，业务代码不再修改；合并/回滚/废止写审计。

但不是密码学级防篡改：没有哈希链/WORM，数据库管理员仍可直接改库。要满足强合规，需要追加哈希链或外部存证，这是未做项。

### Q21：回滚会恢复旧的 ACL、密级、共享关系吗？

不会。版本快照只存内容，不存 ACL/密级/部门/生命周期。

回滚只恢复正文；权限、密级、共享、废止状态保持当前值。这是有意的：不能用内容回滚绕过权限治理。

### Q22：版本号并发冲突时用户看到什么？

后合并者会收到“分块内容已被修改，请刷新后重新提交”或版本号冲突错误；CR 不会半合并，事务回滚。

当前没有自动三方合并/自动重试取号；并发体验是待优化项。

### Q23：这套版本控制什么时候不适用？

- 需要分支/并行版本线：当前是线性 V1.N，没有 branch/merge；
- 需要整篇结构化重写：当前走重解析，不是全文 CR；
- 需要强合规不可篡改：当前只有应用层不可变和审计，没有哈希链/WORM；
- 需要自动合并多人冲突：当前只做乐观锁拒绝，没有 diff3；
- 版本量很大且不清理：快照体积会持续增长，需先做版本压实。

一句话：它解决“正式文档的可追溯、可回滚、可引用”，不解决“代码级分支合并”和“合规级 WORM”。
