# 其他服务如何接入本项目 · 答辩问答

> 一句话：**三条通道——REST/SSE、MCP、CLI；统一用租户 API Key（`X-API-Key`），不继承员工角色，按 capability + KB 白名单授权。**
> 推荐：服务端到服务端接 REST；给 Claude/Cursor 等 Agent 接 MCP；不要给不可信客户端 admin Key。

## 最小接入步骤

1. **company_admin 创建租户 API Key**：`POST /api/v1/tenants/{tenant_id}/api-keys`，指定 `preset=read|write|admin`；token 只在创建时返回一次。
2. **调用方带 `X-API-Key: <token>`** 访问 `/api/v1`；API Key 是独立机器 principal，不是员工 JWT。
3. **按需选接口**：
   - 纯检索：`POST /api/v1/knowledge-search`
   - 问答：先建 session，再 `POST /api/v1/knowledge-chat/{session_id}`（SSE）
   - Agent：`POST /api/v1/agent-chat/{session_id}`
   - 摄入：`write` Key 上传/更新文档
4. **限定 KB**：Key 绑定 KB 白名单；最小权限、按服务单独发 Key、可撤销/轮换。
5. **接 MCP**：设置 `WELLREAD_BASE_URL`、`WELLREAD_API_KEY`，本地用 stdio；远程用 HTTP/SSE 时必须配 `MCP_SERVER_AUTH_TOKEN`。

## 高频追问

### Q1：其他服务能接入吗？有几种方式？

能，三条：

- **REST/SSE**：最通用，适合后端服务、脚本、数据管道；API 前缀 `/api/v1`，Swagger 在 `/swagger/index.html`；
- **MCP**：把知识库、检索、问答、摄入封装成 31 个工具，适合 Claude Desktop、Cursor、Copilot 等 Agent 客户端；支持 stdio/SSE/HTTP；
- **CLI**：适合本机运维/脚本，支持 `WELLREAD_API_KEY` 或 `auth login`。

服务端到服务端优先 REST；Agent 场景优先 MCP；不要把 MCP 当业务 API 网关。

### Q2：怎么鉴权？能用员工账号密码吗？

不能复用员工账号密码。外部接入统一用**租户 API Key**：

- 请求头 `X-API-Key: <token>`；
- API Key 是独立 principal，不继承任何员工角色、部门角色或共享空间身份；
- 权限由 Key 的 capability + KB 白名单决定；
- 员工 JWT 仍用于人工前端，两条 principal 不混用。

不要把 JWT 发给外部服务，也不要把 API Key 当前端登录态。

### Q3：API Key 有哪些权限档位？怎么选？

三档 preset：

- `read`：`retrieve` + `chat` + `read_agents` + `message_history`，只读检索/问答；
- `write`：read + `ingest`，可上传/更新文档，但**不含**建库/删库；
- `admin`：full access，含建库、删文档、模型管理等，风险最高。

给外部服务默认 `read`；确需写入才给 `write`；`admin` 只给可信运维自动化。`manage_kbs`、`manage_models` 不在 read/write 里。

### Q4：能调用哪些能力？精读、协作能接吗？

外部 Key 当前主要开放：

- 检索：`knowledge-search`、MCP `hybrid_search`；
- 问答/Agent：`knowledge-chat`、`agent-chat`；
- 文档摄入：上传、URL、手工 Markdown；
- KB/文档/分块/会话等管理接口按 capability 开放。

**精读、协作、治理是人工业务面，当前不对 API Key 开放**；API Key 不能发起精读或审批 CR。外部服务要做“精读式”处理，只能在自身侧编排检索/问答，或走人工界面。

### Q5：Key 怎么创建？token 丢了怎么办？

由 company_admin 在租户 API Key 管理界面创建，或调 `POST /api/v1/tenants/{tenant_id}/api-keys`。

- 明文 token 只在创建响应里返回一次，列表只显示掩码；
- 丢了不能找回，只能撤销旧 Key、创建新 Key；
- 建议一个服务一个 Key，按服务命名，便于撤销和审计，不要多个服务共用 admin Key。

### Q6：MCP 怎么部署？远程安全吗？

MCP Server 是独立 Python 服务，不存业务数据，只转发到 WellRead 后端。

- 本机单用户：stdio，最简单，不走网络；
- 远程/多客户端：HTTP 或 SSE，启动前**必须**设置 `MCP_SERVER_AUTH_TOKEN`，客户端用 `Authorization: Bearer` 或 `X-MCP-Auth-Token`；
- 网络传输还要限制上传目录 `MCP_ALLOWED_UPLOAD_DIRS`；
- MCP 不额外提权，最终权限仍由 API Key capability + KB 白名单决定。

不要把无鉴权的 MCP HTTP 暴露在公网。

### Q7：API Key 能访问部门共享 KB 吗？

默认不能依赖部门上下文：

- API Key 是公司级 principal，没有部门身份；
- 普通自有/授权范围的 KB 按 Key 白名单访问；
- `list_shared_knowledge_bases` 这类依赖部门共享空间的接口可能返回 403；
- 需要部门共享能力时，应在后端扩展 Key 的部门语义，不要让 Key 冒充员工。

一句话：API Key 能访问“Key 被授权的那部分 KB”，不是“某个员工能看的全部”。

### Q8：外部服务能上传/更新文档吗？写操作边界是什么？

`write` Key 可以上传/更新文档、触发解析和索引；不能建库/删库、不能管理模型。

写操作边界：

- 仍然受 KB 白名单、ACL、密级、部门约束；
- 解析、分块、索引走与人工上传同一条链路；
- 删除文档/分块、建库、模型管理需要更高 capability，默认不给外部服务。

### Q9：有 webhook/事件推送吗？有限流吗？

当前对外是**拉取式**：REST/SSE/MCP，没有通用 webhook/事件订阅；需要异步结果时，调用方自己轮询或消费 SSE。

API Key 目前没有按 Key 的通用限流；生产部署应在网关/入口层加限流、超时和并发保护。不要把“有 API Key”当成“有完整 API 治理”。

### Q10：最小的接入示例？

只做检索：

```bash
curl -X POST http://<host>:6152/api/v1/knowledge-search \
  -H "X-API-Key: $WELLREAD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query":"退费规则是什么","knowledge_base_ids":["<kb_id>"]}'
```

需要问答：先 `POST /api/v1/sessions` 建会话，再 `POST /api/v1/knowledge-chat/{session_id}` 读 SSE。

注意：本地开发的 API 端口是 `6152`，容器内是 `8080`；以实际部署网关为准。

### Q11：推荐怎么给不同外部服务分权？

- 只读问答/检索：`read`，KB 白名单只放必要库；
- 文档同步/入库：单独 `write` Key，不与只读服务共用；
- 管理自动化：`admin` 仅限可信环境，最好再走内网/网关白名单；
- Agent 客户端：MCP + read Key；远程 MCP 再加 `MCP_SERVER_AUTH_TOKEN`；
- 一个服务一个 Key，可撤销、可轮换、可单独审计。

原则：**最小 capability、最小 KB 范围、最短生命周期**。
