# 混合检索与 RRF · 答辩问答

> 用途：答辩 Q&A 速查。
> 核心口径：**四路负责召回覆盖，RRF 负责无量纲融合，Rerank 负责精排**；三层各司其职。
> 优先准备：Q1（k=60）、Q2（为什么不归一化）、Q3（是否四路全跑）、Q4（Rerank 是否让 RRF 多余）、Q5（四路消融）、Q21（ACL）。

## 四路分工与盲区

| 路 | 强项 | 盲区 |
|---|---|---|
| FAISS | 同义改写、模糊描述、语义相似 | 精确文号、编号、型号；字符级差异没有语义信号 |
| BM25 | 精确词、文号、条款号、长尾术语 | 同义改写、长句语义 |
| 元数据 | 机构、产品、文号、日期、密级、部门等结构化过滤与精确匹配 | 问题里没有实体、实体别名未覆盖时失效 |
| Text-to-SQL | 表格类、统计类、聚合类问题 | 非表格类问题、表结构未覆盖的问题 |

## 一、已有问题补答案

### Q1：k=60 怎么定的？为什么不是 50 或 100？

60 是 RRF 原始论文的默认值，**不是我们在小样本上逐点调出来的**。

RRF 只用排名，k 控制头部权重：k 越小，头部排名优势越尖；k 越大，分数越平滑。工程上 10–100 区间通常不敏感，我们选择 60 是为了沿用成熟默认、避免在小评测集上过拟合。

如果评委追问“有没有调过”：没有做正式的 k 扫描。正确做法是固定文档和问题集，扫 k 看 Recall@K 和答案准确率；当前没有这个实验，就不硬报“调过”。

### Q2：四路分数完全不同，为什么不归一化后加权，非要用 RRF？

因为四路分数**量纲不可比**：

- FAISS 是向量相似度；
- BM25 是无界词法分；
- 元数据是规则命中，本质是布尔/枚举；
- SQL 是单结果集，没有候选排名。

min-max、z-score 都要依赖每条 query 的候选分布，分布一变排序就漂；加权还需要标注数据来校准权重，否则只是拍脑袋。

RRF 只看排名，天然免疫量纲、异常分数和不同召回深度；分数级融合留给第二阶段的 cross-encoder rerank。未来如果有稳定标注，可以试加权或 LTR，但当前 RRF 是更稳的零训练基线。

### Q3：每条 query 四路都跑吗？延迟和成本扛得住吗？

**不是每条 query 四路全跑。**“四路”是检索架构，不是每条变体都复制四遍：

- 单步问题：原问题 + 最多 3 条变体；FAISS/BM25 对每条变体各跑一次；元数据按实体跑一次；SQL 按扩展 query 跑一次；
- 多跳/多子问题：planner 每个 step 做轻量 FAISS+BM25+元数据检索（约 top-8），SQL 不参与；
- 路由并行执行，embedding 批量请求，变体生成与 planner 并行；失败有降级路径。

成本主要花在 rerank 和生成，不在四路本身；候选会按源截断，避免把几百条送进重排。

### Q4：图上 Rerank 比纯 RRF 高 1.4~2.1 个点，那 RRF 这层是不是多余的？直接 Rerank 不就行了？

不是替代关系，是**召回融合层和精排层**的区别。

- Rerank 的输入来自 RRF 去重、合并后的多路候选；没有 RRF，就要自己解决分数量纲和候选合并；
- Rerank 是 cross-encoder，有 API 成本、延迟和超时风险；RRF 是零训练、稳定的兜底；
- 图上的 1.4–2.1pp 是 rerank 在融合候选上的增益，不是“RRF 的贡献”，不能反过来推出 RRF 多余。

一句话：RRF 保证“该召回的都进候选”，Rerank 保证“进候选的顺序更准”。

### Q5：四路各自贡献多少？做过消融吗？

**没有做过完整四路消融**，不能编一个贡献百分比。

现有证据是：

- 四路盲区互补（见上表）；
- 检索 trace 能看到每条候选来自哪些路、RRF 来源和 rerank 分数；
- 线上 badcase 能定位到“某一路长期没命中”的类型。

要严谨回答贡献，应该固定文档和问题集，逐路开关（FAISS-only、BM25-only、+元数据、+SQL），报告 Recall@K、MRR/nDCG、引用正确率和答案准确率。这是下一步评测，不是当前已有结论。

### Q6：Rerank 用的什么模型？为什么？

`BAAI/bge-reranker-v2-m3`，cross-encoder，中英和多语言支持较好，可本地部署也可走网关。

选它而不是 LLM 打分，是因为延迟和成本更低、输出更稳定；超时 5 秒、失败降级回 RRF，不让精排成为单点故障。

### Q7：Rerank 前取多少条？为什么是这个数？

- FAISS 50 条、BM25 50 条、元数据 20 条、SQL 1 条；
- 送入 rerank 前按源截断，每源最多 100 条（实际通常远小于此）；
- 单条文档截前 5000 字，控制 API 输入；
- 最终输出 10 条给 LLM。

这是“召回广度 vs 延迟/成本”的折中：再往上加候选，精排收益递减，API 延迟明显上升；往下减，容易丢长尾。

### Q8：四路盲区怎么发现的？

不是模型自动诊断，是 **badcase + 检索 trace + Recall@K 曲线**人工归因：

- 某类问题 FAISS 长期 0 命中 → 精确编号/文号类；
- 某类问题 BM25 命中差 → 同义改写/长句；
- 问题没有实体，元数据路失效；
- 非表格问题 SQL 不命中。

PPT 里的四条盲区是这些 badcase 的归纳。trace 能拆出四路 hit、RRF 候选和 rerank 分数，方便复盘。

## 二、新增高概率追问

### 融合与排序

### Q9：元数据和 SQL 没有排名，怎么套 RRF 公式？

它们是**固定 boost 的 rank-1 代理**：

- 元数据精确匹配：`1/(k+2)`，比普通 rank-1 的 `1/(k+1)` 略低，保证有优势但不垄断；
- SQL 单结果：`1/(k+1)`，独立 key，不参与普通 chunk 去重；
- 元数据候选在 rerank 后还有 0.1 分阈值，弱匹配会被丢弃，不会因为固定 boost 强行占名额。

所以公式里的 rank 只适用于 FAISS/BM25；规则路用固定小分母表达“高置信但有限”。

### Q10：同一个 chunk 被 FAISS 和 BM25 同时命中，分数怎么算？

以 `chunk_id` 为 key，多路 RRF 分**相加**，只占一个候选位，`sources` 记录命中的来源。

这是 RRF 的共识加权：两路都认为相关，排名应更靠前。多 query 变体则在各自路线内先按最高分合并，再进入 RRF，避免同一变体重复计分。

### Q11：候选深度为什么是 50/50/20/1？

- FAISS/BM25 各 50：对称召回，覆盖语义和词法长尾；
- 元数据 20：足够覆盖实体精确匹配，再多也会被 rerank 过滤；
- SQL 只返回一个结果集：它是聚合/表格答案，不是 chunk 列表；
- 最终 10 条：控制 LLM 上下文和生成成本。

不是拍脑袋的固定值，是按“每路召回成本 + rerank 输入成本 + 最终上下文预算”倒推的。

### Q12：Rerank 超时或失败怎么办？会不会整条链路挂掉？

不会。Rerank 失败/超时返回空，系统**降级为 RRF 排序 + 源配额**，继续回答；日志里能看到降级。

单步 A/B 可以配置跳过 rerank 省约 1.3 秒，但线上默认开启；Rerank 是增强，不是单点依赖。

### Q13：为什么最终只给 10 条？元数据配额为什么是 3/5？

- 10 条是生成阶段的上下文预算：再多会挤占答案空间、增加成本和幻觉风险；
- 单文档问题元数据最多 3 条，跨文档最多 5 条，防止精确匹配挤掉语义召回；
- 低分元数据会被 rerank 阈值过滤，不强制占位；
- SQL 命中作为独立候选进入最终结果，不参与元数据/语料的 3/5 配额计算，但仍受最终 top10 截断。

配额本质是“精确匹配、语义召回、结构化结果”三种证据的平衡。

### Q14：章节覆盖和邻域去重是什么？为什么不是直接取 topK？

直接取 topK 容易被单章节的高分碎片占满，概述类问题会缺章节；父块和相邻子块同时入选也会重复。

现在的做法是 rerank 后按（文档, H2, H3）做三轮贪心：每章先取 1 条高分，未覆盖章节补位，剩余按分数补；同文档相邻 chunk 跳过，父块扩展补上下文。

代价是排序不再是纯分数序，但覆盖率和答案完整性更好。

### 查询与成本

### Q15：查询变体怎么生成？失败了怎么办？变体也跑四路吗？

变体由 LLM best-effort 生成，最多 3 条，超时或解析失败直接返回空，不影响主查询。

变体只扩 FAISS/BM25（语义和词法路），元数据和 SQL 不按变体复制；各路变体结果先按 chunk 最高分合并，再进 RRF。

### Q16：延迟怎么控？有没有 P95 数据？

控制手段：路由并行、embedding 批量请求、planner 与变体并行、rerank 候选截断、5 秒超时降级、最终 10 条。

**没有做专门的 P95 压测**，所以不报一个好看的数字；线上用 SSE trace 拆“检索/融合/精排/生成”各阶段耗时，按真实瓶颈优化。

### Q17：多跳/多子问题怎么检索？和单步有什么不同？

planner 把问题拆成 `parallel_subq` 或 `multi_hop`，每个 step 走轻量 FAISS+BM25+元数据检索（约 top-8），SQL 不参与；候选合并后统一做 ACL/引文。

精排时对原问题和各 step query 分别打分取最大值，避免原问题语义稀释子问题。代价是 planner 本身多一次 LLM 调用，失败会退化为单步检索。

### 质量与边界

### Q18：四路消融没做，那 Recall@K 图能说明什么？

图说明的是 **rerank 在现有融合候选上的增益**，不能说明四路各自的贡献，也不能说明 RRF 单独的价值。

它回答的是“精排有没有用”；要回答“每路有没有用”，需要按路开关做消融。这两个问题不能混在一起说。

### Q19：这套四路是不是过度设计？小语料也需要吗？

小语料、单模态、纯精确查询时，四路 + rerank 确实偏重，可以退化到单路或跳过 rerank。

我们保留四路是因为企业语料同时有制度、合同、表格、编号和口语化问题，单路会在某类问题上系统性漏召回；当前规模下并行成本可控。

### Q20：为什么不直接上学习排序（LTR）/加权融合？

LTR 需要稳定标注和特征工程，当前没有足够标注；加权融合需要跨 query 校准，容易过拟合。

RRF 是零训练、可解释、对量纲免疫的基线；先保证不崩，再谈用标注换最后几个点。未来有评测集可以试 query-type 权重或 LTR，但要先证明收益。

### Q21：ACL 在检索哪一步生效？SQL 路怎么防越权？

单步路径在每一路检索后、融合前就按 `acl_scope` 过滤；多跳路径在 planner 合并后、进入精排前统一过滤；融合后还有一次兜底过滤。无论哪条路径，**无权文档都不会进入 rerank 或答案**。

- 缺 `acl_scope` 直接 fail-closed，不提供未过滤兜底；
- KB、密级、部门同样在候选级过滤；
- SQL 路有行级 KB 作用域，密级按所涉表格所属文档的最严格值处理；
- 精读/问答的引用还会再复核一次文档权限。

所以不是“先检索再藏起来”，而是无权限内容不进入最终候选集。

### Q22：什么情况下这套方案不适用？

- 语料很小、问题几乎都是精确查询：单路 BM25 可能就够；
- 延迟极敏感、不能接受 rerank：可以关闭精排，退化到 RRF；
- 问题几乎全是表格/统计：SQL 权重应更高，语义路是补充；
- 没有实体元数据：元数据路贡献会很低，不应强行占配额。

方案不是“四路越多越好”，而是按语料和问题类型选召回路；当前配置是面向企业混合语料的默认值。
