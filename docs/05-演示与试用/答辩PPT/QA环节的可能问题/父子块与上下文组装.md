# 父子块与上下文组装 · 答辩问答

> 用途：答辩 Q&A 速查。
> 核心口径：**child 是检索单位，parent 是生成单位；上下文不是越多越好，而是按题型和预算组装。**
> 优先准备：Q1（300/1200）、Q2（为什么只取 top1 parent）、Q3（1500 截断）、Q6（六层是否每次都有）、Q9（预算分配）、Q15（引用指向谁）。

## 六层上下文在实现里分别落在哪

| 层 | 实际位置 | 何时出现 |
|---|---|---|
| 系统规则 | `<system>` | 每次都有 |
| 中间结论 | `<intermediate_results>` | 仅多跳/多子问题 |
| 文档摘要 | `<documents>` 最前面的 `【文档摘要】` | 仅多跳，最多 3 篇 |
| 结构化 SQL | `<documents>` 内的 `[结构化查询结果]` | 仅 SQL 命中 |
| 检索上下文 | `<documents>` 内的 parent/child 条目 | 每次有检索结果 |
| 用户问题 | `<user_question>` | 每次都有 |

所以“六层”是内容角色，不是固定六段；普通问答通常只有系统规则、检索上下文、用户问题三层。

## 一、父子块

### Q1：为什么 child 300、parent 1200？这个比例怎么定的？

这一页按 300/1200 讲，是当前演示配置；系统里这两个值按知识库可配。

- **child 小**：作为向量检索单位，语义更聚焦，召回精度高，噪声少；
- **parent 大**：作为生成上下文，保留完整句子、段落和前后条件，避免“只拿到半句话”；
- 比例约 1:4：child 负责“找得到”，parent 负责“读得懂”。

没有做过大规模调参证明 300/1200 是全局最优；它是经验区间。child 再大，语义会被稀释；再小，单块信息不足。真正上线应按语料和评测集调。

### Q2：为什么只给 top1 取 parent，其他不给？多文档时每篇都取 parent 吗？

**不是每篇文档都取 parent。** 当前是每个来源桶（元数据/语料/SQL）的第 1 条取 parent，其余候选取 child。

原因是预算：如果 5 篇文档各塞一个完整 parent，token 很快爆掉，而且大部分是重复背景。top1 parent 保证“最相关的那一段有完整上下文”，其他 child 负责补不同章节/不同文档的证据。

多文档对比题靠 rerank 配额、章节覆盖和摘要前置保证每篇都有代表，而不是每篇都给一个完整 parent。

### Q3：parent 截 1500 字符，会不会把答案截掉？

会丢尾部，这是明确的预算边界。

当前 parent 只保留前 1500 字符（章节主体），因为尾部经常是冗余操作细节；如果答案恰好在尾部，可能被截掉。补偿手段是：

- 其他 child 命中可以补回尾部；
- 重叠/相邻 span 会合并重建；
- 多跳题用文档摘要和中间结论补全局信息。

不是无损方案，是用“上下文预算”换“覆盖更多来源”。

### Q4：父子块怎么切？怎么保证不重不漏？

父块和子块来自同一份文本，child 是 parent 内的子区间，带位置坐标；不是两次独立切分。

- 父块按章节/段落边界切，保留完整句；
- 子块在父块内继续切小，作为 embedding 单位；
- 合并上下文时用并集区间重建，避免重叠重复；
- 跨章节不合并，保证列表式问题各章节独立成条；
- 组装前先按文档版本去重，只留最新版。

### Q5：多文档对比题，怎么保证每个文档都有上下文？

靠三层：

1. rerank 的源配额（元数据/语料）和章节覆盖，避免单文档占满；
2. `_select_diverse` 按（文档, H2, H3）每章先取一条，未覆盖章节补位；
3. 多跳题把涉及文档的摘要前置（最多 3 篇），给模型全局导航。

不保证“每篇都给 parent”，但保证“每篇都有代表证据”；如果某篇完全没被召回，组装层无法凭空补出来。

## 二、上下文窗口与拼装

### Q6：六层上下文是每次都全有吗？

**不是。** 六层是按“内容角色”拆的，不是固定六段：

- 普通问答：`<system>` + `<documents>` + `<user_question>`；
- 多跳/多子问题：多一段 `<intermediate_results>`（中间结论）；
- 文档摘要、结构化 SQL 是 `<documents>` 里的子层，只有触发时才出现；
- 没有 SQL 命中就没有 SQL 层，没有多跳就没有中间结论层。

答辩时说“按需注入、逐步补充”，不要说“每次六层都塞满”。

### Q7：为什么这样排序？模型会不会忽略中间？

顺序是：系统规则 → 中间结论（多跳时）→ 文档证据（摘要/SQL/chunk）→ 用户问题。

- 稳定规则放最前，保证约束不被长文档稀释；
- 用户问题放最后，紧贴生成；
- 证据放中间，用 XML 标签隔离，防止文档内容被当成指令。

“中间遗忘”是长上下文风险，靠 8000 字符预算、top1 前置、摘要导航缓解，不能承诺完全消除。

### Q8：8000 字符的预算怎么定的？token 怎么算？

`MAX_CONTEXT_CHARS=8000` 是字符预算，约几千 token（中文近似 1 字 ≈ 0.6–1 token，具体看模型分词）。

它不是模型窗口上限，而是给成本、延迟和“中间遗忘”留余量：窗口能放更多，不代表应该放更多。预算是可配的，换模型/换语料可以调。

### Q9：超预算为什么前 3 条全量、后面均分？会不会漏掉后面的关键证据？

这是“头部保深度、尾部保覆盖”的策略：

- 前 3 条是 rerank 榜首，最可能包含答案，给全量；
- 剩余条目按剩余预算均分，每条设最低字符下限（约 300），保证多来源都有代表；
- 不是简单“尾丢”，避免多文档对比题整条来源被丢掉。

代价是后面的条目会被截断，可能漏细节；这是预算约束下的折中，不是无损。真要保尾部，需要加预算或减少来源。

### Q10：结构化 SQL 结果怎么和文档块共存？

SQL 命中时作为独立候选进入上下文，标记为 `[结构化查询结果]`，不参与普通 chunk 的元数据/语料配额。

- 数据查询类问题会把上下文上限收紧（约 4 条），因为答案主体在结构化结果里，语料块多是噪声；
- 普通文档块仍保留，用于解释口径、补充定义和引用；
- SQL 结果与文档块都受 ACL、密级、KB 作用域约束。

### Q11：文档摘要什么时候注入？摘要错了怎么办？

只在多跳/多子问题路径（planner_multi）注入，取涉及文档的前 3 篇摘要，放在上下文最前，作为导航。

摘要不是答案依据：最终回答仍以检索 chunk 和引用为准；摘要错了可能误导模型选错章节，但不会单独构成答案。摘要可重新生成，属于可修正的辅助层。

### Q12：中间结论是什么？中间错了会不会传染到最终答案？

中间结论是 planner 每个 step 的轻量检索+作答摘要，放在 `<intermediate_results>`；最终合成时同时看中间结论和原始上下文，不是只信中间结论。

风险存在：中间步骤错了，最终答案可能被带偏。缓解是保留原始 chunk、允许合成阶段纠偏；planner 失败/超时会退化为单步检索。当前没有对中间结论做强制校验，这是边界。

### Q13：相邻/重叠 chunk 怎么合并？跨章节为什么不合并？

同文档、span 重叠或相接的上下文会合并成并集区间，按 child 单元重建正文，避免重复又不断裂。

跨章节不合并：列表式/对比式问题需要每章独立成条，合并会把“第一条、第二条”揉成一段，模型容易漏项。合并是局部补全，不是全局压缩。

### Q14：child 完全落在 parent 内就跳过，坐标可靠吗？

坐标来自解析阶段的 chunk 位置，启动时预计算 parent 映射；child 完全落在已收录的完整 span 内才跳过，局部 child 不能作为覆盖证据。

坐标缺失、越界或 reparse 后重建时，系统保守跳过或按 child 处理，不做激进合并。reparse 会重建坐标，旧锚点失效是已知代价。

### Q15：引用指向 child 还是 parent？

**引用指向 child。** parent 只给模型提供上下文，引用列表来自 rerank 的 child 候选。

这样引用能定位到具体片段，而不是整篇文档；parent 内容包含 child，所以上下文和引用不矛盾。

### Q16：如果 rerank 的 top1 错了，parent 会不会放大错误？

会。top1 错，parent 会把一段不相关的完整上下文放大，这是 parent 策略的风险。

缓解手段是多路召回、rerank、章节覆盖和 child 证据；但不能保证 top1 永远对。所以引用仍指向 child，评测要看 top1 命中率和引用正确率，而不是只看答案流畅度。

### Q17：ACL、版本、废止在组装的哪一步生效？

都在候选阶段，不在拼装阶段：

- ACL/密级/部门在检索后、融合/精排前过滤；
- 版本先去重，只留最新版文档；
- 废止文档默认在检索阶段剔除（精读显式选中文档例外）；
- 组装层只拿已授权、已过滤的候选，不会把无权内容拼进上下文。

### Q18：为什么不直接塞整篇文档，或者用长上下文模型？

整篇文档 token 成本高、首字延迟高，而且长上下文存在中间遗忘；引用粒度也会退化成“整篇”，无法定位段落。

parent 给局部完整上下文，child 给检索精度，摘要给全局导航——三层拼起来比“整篇硬塞”更可控、更可引用。

### Q19：这套组装策略评测过吗？指标是什么？

没有做过“child-only / parent-only / 当前组装”的单独消融；现有评测是端到端问答准确率、Recall@K、引用可定位率和人工抽检。

要证明组装策略的贡献，需要固定文档和问题集，对比三种策略的答案准确率、引用正确率和 token 成本；这是下一步评测计划，现在不硬报数字。

### Q20：parent 映射缺失、上下文为空怎么办？

- chunk_store 不可用时，退回原始 child 文本，不做 parent 扩展；
- parent 映射缺失时跳过该条，避免拼错上下文；
- 上下文为空时返回“未找到”，不伪造；
- 降级会留日志和 trace，便于定位是解析、索引还是组装问题。

## 三、边界与取舍

### Q21：什么情况下父子块策略不适用？

- 短问答、单段事实查询：parent 的上下文优势不明显，反而增加 token；
- 语料很小、单文档：直接整篇或 child 就够；
- 问题需要跨全文汇总：parent 只覆盖局部，需要摘要/多跳；
- 文档结构极乱、坐标不可靠：父块映射容易错，需要先修解析。

### Q22：如果让你重做，会改哪里？

优先补三件事：

1. 做 child-only / parent-only / 当前策略的消融，证明 parent 的真实收益；
2. 把 parent 截断从固定 1500 改成按章节/句边界动态截断；
3. 对中间结论和摘要加可验证的引用，减少错误传染。

这三项比继续调 300/1200 更有价值。
