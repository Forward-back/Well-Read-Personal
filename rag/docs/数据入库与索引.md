# 数据入库与索引

本文描述 App 分块如何进入 RAG、写入 MySQL 与 FAISS，以及删除、重嵌和重建索引。架构见[系统架构](系统架构.md)，接口字段见[接口与集成](接口与集成.md)。

## 1. 入库路径

```mermaid
flowchart TB
    A[App 上传/同步文档] --> B[App 解析、OCR、分块]
    B --> C[/ingest 推送 document + chunks + meta]
    C --> D[事务内替换旧文档]
    D --> E[(MySQL documents/chunks)]
    D --> F[BGE embedding]
    F --> G[(FAISS HNSW)]
    E --> H[重载内存镜像]
    G --> H
    H --> I[可检索]
```

RAG 不再扫描 `Data/` 做离线解析，也不再自带 PDF/DOCX/XLSX 解析器、领域分块器或元数据抽取。App 未携带 `chunks` 的请求会被拒绝。

## 2. 幂等与事务

- `/ingest` 以 App 的 `document_id` 为幂等键；重复推送会在同一事务内删除旧文档及其分块，再插入新版本。
- 旧行删除与新行写入同事务提交；新行写入失败时回滚，保留旧版本，不会出现“文档消失”。
- 嵌入失败时保留分块但把文档标为 `failed`，App 重新推送即可重试；不把无向量文档标成 `success`。
- `/delete_document` 按 `document_id` 删除文档，MySQL 级联清分块与日志，然后重载内存镜像。
- FAISS HNSW 不支持物理删除；删除后靠 `vector_id` 映射过滤，`rebuild_faiss.py` 做物理重建。

## 3. 分块契约

每个 App 分块至少包含：

| 字段 | 说明 |
|---|---|
| `id` | App chunk 稳定 ID，写入 `chunks.source_chunk_id`，用于引用与来源锚点 |
| `chunk_index` | 文档内顺序 |
| `content` | 分块文本；空块被跳过 |
| `chunk_type` | `text` 或 `image` |
| `start_at` / `end_at` | App 原文偏移，写入 `position_start/position_end` |
| `parent_chunk_id` | 图片块所属 App 文本分块 ID |
| `image_url` / `image_caption` / `image_ocr` | 图片块字段 |

文本块进入嵌入；图片块以 caption/OCR 文本参与召回，不把图片本体传给生成模型。RAG 不生成 parent 行，当前 App 入库路径全部为 child 单元。

## 4. 元数据

`/ingest` 可选字段写入 `documents` 并反范式到 `chunks`：

| 字段 | 说明 |
|---|---|
| `doc_title` / `file_name` / `file_type` | 展示与引用 |
| `doc_number` / `org_name` / `doc_date` / `doc_type` / `product_name` | 文档属性 |
| `lifecycle_status` / `effective_date` / `expiry_date` / `superseded_by` | 兼容旧数据；个人版默认 `effective` |
| `custom_metadata` | App 受控 KV |

RAG 不接收部门、密级或 ACL 字段。`/update_metadata` 可原地更新生命周期字段，不重切分、不重嵌入。

## 5. 嵌入与索引

- BGE-M3，取前 768 维；批量 embedding，失败逐条回退。
- 写入 `chunks.vector_id`，状态从 `pending` 变为 `embedded`；FAISS HNSW `M=32`、`ef_search=192`。
- 索引文件 `faiss_index.bin` 在 `RAG_DATA_DIR` 的父目录；容器内挂载 `/app/external`。
- 重嵌 daemon 每 `REEMBED_INTERVAL_MINUTES` 分钟重试 `pending` 分块；`<=0` 关闭。
- 本地 BGE 与网关 embedding 向量不同源，切换必须重建索引。

## 6. 数据库对象

| 表 | 关键字段 | 说明 |
|---|---|---|
| `documents` | `source_doc_id`、`knowledge_base_id`、`parse_status`、`chunk_count` | App 文档镜像 |
| `chunks` | `document_id`、`vector_id`、`chunk_level`、`status`、`source_chunk_id`、图片字段、文档属性 | 召回单元与引用锚点 |
| `parse_log` | `stage`、`status`、`message` | 入库日志 |
| `chunk_embedding_cache` | `text_hash`、`dim`、`embedding` | 旧向量缓存，当前无读写 |

旧版表格/产品检索表（`tables_structured`、`schema_registry`、`product_mentions`）已从 `init.sql` 与代码中移除：新环境不再创建，已有库中的旧表不再被读写，可按需手工删除。

## 7. 入库验证

```sql
SELECT parse_status, COUNT(*) FROM documents GROUP BY parse_status;
SELECT chunk_level, status, COUNT(*) FROM chunks GROUP BY chunk_level, status;
SELECT COUNT(*) FROM chunks WHERE chunk_level='child' AND status='pending';
```

期望：

- `documents.parse_status` 全部 `success`（失败文档会被 App 重推）。
- 当前 App 路径下分块全部为 `child`，`status=embedded`。
- `pending=0` 或由重嵌 daemon 处理中。

`GET /index/status` 返回向量数、文档数、分块数、pending/failed 数与索引文件状态。

## 8. 重新入库与重建

以下情况必须重建索引：

- 切换 embedding 模型或维度。
- 修改 App 分块策略导致分块 ID/文本整体变化。
- 批量替换语料后旧文档残留。
- FAISS 与 MySQL `vector_id` 错位。

步骤：

```sql
DELETE FROM documents;
```

删除 `faiss_index.bin`，重启容器让 entrypoint 建空索引，再由 App 逐篇重推。容器内也可运行：

```bash
python rebuild_faiss.py
```

只清 MySQL 不重建索引、或只重建索引不清 MySQL，都会造成映射错位。

## 9. 当前限制

- 模型与索引不随 git/镜像分发，必须通过 `data/rag/` 挂载。
- 图片质量依赖 App 的 OCR/VLM 结果；RAG 不重新识别图片。
- HNSW 删除是逻辑过滤，长期运行或大量删除后需要重建。
- 旧表与旧生命周期字段仍保留，兼容历史数据但不参与个人版主流程。
